## 一、会议背景与目标

用户已对钱迹 App v4.5.3（包名 `com.mutangtech.qianji`）完成静态逆向分析。本项目拟**复刻一个自用版记账应用 SuijiLedger**，并**兼容钱迹的数据导入导出**，实现个人账本数据的自主可控。

会议目标：

1. 基于逆向分析事实，确定 SuijiLedger 的功能范围与优先级；
2. 确定"钱迹数据兼容"的准确技术口径（能读什么文件、能写什么文件）；
3. 确定技术栈与总体架构；
4. 分解开发任务、里程碑与验收标准。

## 二、系统分析师（SA）汇报：逆向分析关键事实

SA 汇报了源码级调研结论（均有代码证据，详见 SRS 附录 A）：

### 2.1 核心数据模型（`data/model/`，149 个实体类）

- **Bill（账单）** 是核心实体：`money` 为 **double 元**（非分）、`timeInSec` 为 Unix 秒、业务主键 `billid`（导出时格式化为 `"qj" + billid`）、本地自增 `_id` 与服务端 ID 双轨并存（同步去重依据）。
- **账单类型 `type` 共 14 个取值**：0 支出、1 收入、2 转账、3 信用卡还款、4 收款（债）、5 报销、6 借入、7 借出、9 还款、10 利息支出、11 利息收入、20 退款、21 已报销、22 报销包。
- **账户引用三字段**：`assetid`（单账户）/ `fromid` → `targetid`（转账与债类），账户快照名冗余存 `fromact`/`targetact`。
- **BillExtra**：手续费 `transfee`（正数=手续费、负数=优惠券）、`flag`（1 不计入收支 / 2 不计入预算）、标签 `tags`、退款与报销的关联子账单。
- 分类为**二级结构**（`Category.level` 1/2 + `parentid`），账本 `Book`、资产账户 `AssetAccount`（含 `credit` 额度、`incount` 是否计入净资产、`stype` 账户子类型）、预算 `Budget`（月/年/日期区间 + 分类维度）、标签 `Tag`、分期 `Installment`、周期任务 `RepeatTask`。
- 会员体系（User.vipType 等）、自动记账、多账本共享为**服务端驱动**功能，本地复刻无意义（见 2.3）。

### 2.2 导入导出格式（兼容性依据，`dataexport/exportor/`）

- **导出三种格式**：CSV / XLSX（Apache POI）/ JSON，**列结构完全一致**，共 19 列：
  `ID, 时间, 账本, 分类, 二级分类, 类型, 金额, 币种, 账户1, 账户2, 备注, 已报销, 手续费, 优惠券, 记账者, 账单标记, 标签, 账单图片, 关联账单`
  （证据：`Bill.getCsvTitle()`、`Bill.toExportRow()`）
- 关键格式细节：ID = `qj{billid}`；标签以 `#` 分隔（`BillExportorFactory.TAG_STR_SEPARATOR`）；账单标记取值 `nc` / `nb` / `nc&nb`；金额为数值元；类型为中文名（"支出/收入/转账/还款/报销/退款/借入/借出/收款/利息支出/利息收入"等）。
- JSON 导出每行字段：`key/date/category/type/money/currency/asset/from/target/remark/hasbx/fee/coupon/username/billflag/images/sourceid`。
- **钱迹的导入是"上传文件 → 服务端解析 → 返回账单包（ImportPack）→ 用户确认入库"**，客户端不做本地解析（证据：`network/api/dataimport/C4923a.java` 的 `import/submitfile`、`import/packbills`；App 内无 CSV 解析代码）。ImportPack 会预览"新增账户/新增分类/新增标签"供用户确认。

### 2.3 对复刻范围的影响

- 钱迹的**强服务端功能**（账号体系/云同步/会员支付/多账本共享/自动记账 OCR/无障碍监听）无法也不应复刻——我们的定位是**自托管单机优先**。
- 钱迹的 **VIP 门禁**（自动记账、多账本上限、资产分组、账单图片、分期>2、周期>2、Excel 导出等）在 SuijiLedger 中**全部免费开放**（自用无商业诉求）。

## 三、产品经理（PM）提案：产品定位与功能范围

PM 提出产品定位：**"钱迹的个人自托管平替"——数据 100% 自有、部署一份、全家可用、随时迁入迁出钱迹生态。**

### 3.1 版本范围决议（P0/P1/P2）

| 优先级 | 范围 |
|---|---|
| **P0（MVP 必须）** | 记账（支出/收入/转账 + 手续费）、多账本、二级分类管理、资产账户与净资产、账单流水（月汇总/日分组）、统计图表（趋势/分类占比）、搜索筛选、数据导入导出（钱迹 CSV/XLSX/JSON + 微信/支付宝 CSV + 自有全量 JSON 备份）、深色模式 |
| **P1（第二迭代）** | 预算（总/分类）、报销与退款、标签、周期记账、借还（债权债务）、信用卡还款、桌面端适配、PWA 离线 |
| **P2（远期）** | 分期记账、存钱计划、多用户（家庭成员）、WebDAV 自动备份、英文界面 |

### 3.2 关键产品决策

1. **金额精度改进**：钱迹用 double 存元存在浮点误差隐患；SuijiLedger **内部以整数"分"存储、展示层格式化元**，导入导出时与钱迹的"元"格式双向无损转换（保留 2 位小数）。
2. **类型收敛**：P0 支持 type ∈ {0,1,2,3,20}（支出/收入/转账/信用卡还款/退款）；其余类型在**导入时不丢失**（落库保留 type 与全部字段，界面显示为"其他"并可查看详情），P1 逐步开放编辑。
3. **导入预览确认**：沿用钱迹 ImportPack 的交互范式——解析后展示"将新增 N 个分类/M 个账户"预览，用户确认映射后入库。
4. **不做**：支付/会员/广告/推送/社交登录/自动记账（无障碍与 OCR 涉及高敏权限，自托管场景收益低）。

## 四、系统架构师（Arch）提案：技术选型（会议决议）

| 层 | 选型 | 理由（含备选） |
|---|---|---|
| 前端 | **Vue 3 + TypeScript + Vite + Pinia + Vant 4 + ECharts** | 移动优先复刻钱迹交互；Vant 提供成熟移动组件（数字键盘/日历/下拉刷新）；备选 React+AntD Mobile（团队不熟，弃） |
| 后端 | **Node.js 20 LTS + NestJS + Prisma ORM** | 前后端同构 TypeScript；NestJS 模块化契合"账单/账本/资产/导入导出"领域划分；备选 Go+Gin（跨语言维护成本高，弃） |
| 数据库 | **SQLite（单文件）** | 自部署零运维、`cp` 即备份；Prisma schema 可平迁 PostgreSQL（多用户并发时） |
| 兼容层 | **exceljs + csv-parse + iconv-lite** | 读写 xlsx/csv；微信/支付宝账单 CSV 为 **GBK 编码**，需 iconv-lite 转码 |
| 部署 | **Docker Compose 单容器**（静态前端 + API 同进程） | 树莓派/NAS/云主机均可跑；数据卷挂载 SQLite 文件与上传图片目录 |

架构要点决议：

- **API 风格 REST + OpenAPI**；鉴权 P0 用单管理员口令（JWT），P1 扩展多用户。
- **兼容层独立成包 `packages/qianji-compat`**（纯函数、无框架依赖），前后端与 CLI 均可复用，导入导出逻辑必须与业务解耦并 100% 单测覆盖。
- 金额、时间一律 `integer 分` / `bigint 毫秒`；对外 DTO 转换集中在兼容层。

## 五、前端（FE）与后端（BE）意见与风险

**FE：**
- UI 采用底部五 Tab（明细 / 图表 / ➕记一笔 / 资产 / 我的），记一笔为全屏页：金额键盘 + 分类宫格 + 展开区（账户/日期/备注/标签/报销），对齐钱迹肌肉记忆；
- 需要后端提供**游标分页 + 按月聚合**接口，避免移动端全量拉取；
- 数字键盘组件自研（Vant 无带运算的记账键盘）。

**BE：**
- SQLite 写并发低（单写者），家庭自用足够；API 层加事务与幂等键（导入批次 `importBatchId`）防重复导入；
- 导入 10 万行级账单需流式解析 + 分批写库（500 行/事务）+ 进度上报（SSE）；
- 图片附件 P0 存本地磁盘（`/data/uploads`），URL 形态兼容钱迹"账单图片"列。

**SA 风险提示（会议确认纳入风险清单）：**

| # | 风险 | 对策 |
|---|---|---|
| R1 | 钱迹导出格式未来变更 | 兼容层做**格式版本探测**（列头指纹），单测固化 v4.5.3 样例 |
| R2 | 微信/支付宝 CSV 格式随平台改版 | 解析器插件化，按"列头签名"路由；失败行原样导出到错误报告 |
| R3 | type=6/7/9 等债类账单语义复杂（账户引用方向不同） | P0 只读不丢数据；P1 实现编辑前先写领域测试 |
| R4 | SQLite 损坏 | 每日自动备份（保留 30 份）+ 启动时完整性检查 |

## 六、会议决议

1. **通过**产品定位与 P0/P1/P2 范围（§3.1）；
2. **通过**技术选型（§四），monorepo 结构 `apps/web + apps/server + packages/qianji-compat`；
3. **确认兼容口径**：能导入钱迹导出的 CSV/XLSX/JSON；能导出同构 CSV/XLSX；能导入微信/支付宝原始账单 CSV；另提供自有全量 JSON 备份（含全部实体）；
4. 责成 PM 输出《02_需求规格说明书》、FE 输出《03_UI设计稿》、Arch+BE 输出《04_开发任务书》，本轮完成；
5. 里程碑：M1 骨架+记账闭环 → M2 流水+统计 → M3 资产+预算 → M4 兼容导入导出 → M5 打磨发布（详见开发任务书）。
